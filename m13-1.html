第 13 章 TCP の接続と信頼性　13-1

「会話できる状態」を作ってから話し始める

このページでわかること

IP は届く保証をしないという前提のうえで、送ったデータを送った順番のとおり抜け落ちなく届ける役目を引き受ける仕組みがある。データのやり取りを始める前に、送り手と受け手はまず 3 回の合図をやり取りして「会話できる状態」を作る。このページでは、その仕組みと、3 回の合図の中身を確認する。

このページの目次

かけあい

第 6 章で、IP は届く保証をしないっていう話を聞いたんですけど、じゃあ届いたかどうかは誰が確認してるんですか?

それを引き受けるのが TCP です。送ったデータを、送った順番のとおり抜け落ちなく届くように管理する通信の方法で、届いたことの確認も TCP 自身が行います。第 1 章で見た層の話でいうと、IP の一つ上の層で動く仕組みです。

送り手と受け手は、何をもとに区別されるんですか?

IP アドレスとポート番号の組(ソケットと呼びます)で区別されます。この組ごとに、別々の TCP 接続を作れます。

じゃあ、TCP を使えばもうデータを送っていいんですか?

まだです。データを送る前に、まず送り手と受け手の間で会話できる状態を作ります。これが、第 1 章で見た「会話できる状態」の正体で、TCP 接続と呼びます。

その「会話できる状態」って、具体的にどうやって作るんですか?

送り手と受け手が 3 回、決まった合図をやり取りします。この手順を TCP ハンドシェイク、または 3 ウェイハンドシェイクと呼びます。

3 回のやり取りって、具体的には何を送り合うんですか?

まず送り手が「始めたい」という合図(SYN)を送ります。次に受け手が「始めたい、かつ了解した」という合図(SYN/ACK)を返します。最後に送り手が、届いたことを知らせる合図(ACK)を返します。

その ACK、名前は聞いたことある気がします。もっと詳しく知りたいです。

届いたことを知らせる仕組みとしての ACK は、次のページ(13-2)で詳しく扱います。今日はまず、なぜ 2 回ではなく 3 回のやり取りが必要なのかを見ていきましょう。

なんで 2 回のやり取りだけじゃ駄目なんですか?

お互いが持つ情報が一致したことを確認するには、3 回のやり取りがちょうど過不足ない回数だからです。2 回だと、最後に送った側は相手にちゃんと伝わったかまでは確認できません。

3 回目の ACK で、送り手側も「ちゃんと伝わった」って確認できるってことですね。

そのとおりです。これで両側とも、お互いの情報が一致したことを確認できます。

UDP だと、こんな手順は要らないんですよね?

そうです。UDP は事前の手順を踏まずにいきなりデータを送りますが、TCP は会話できる状態を作ってから送ります。この違いが、それぞれの向き不向きにつながります。

この 3 回のやり取りがうまくいかないと、接続自体が失敗するってことですね。

そのとおりです。相手が応答しない、または応答できない場合、会話できる状態は作れません。実際に自分の Mac から試して確かめてみましょう。

会話できる状態ができたら、もうデータのやり取りが始まるんですね。

そうです。次のページでは、送ったデータがどうやって届いたと確認されるかを見ていきましょう。

まとめ

  • TCP は、送ったデータを送った順番のとおり抜け落ちなく届くように管理し、届いたことの確認も行う通信の方法である。送り手と受け手は IP アドレスとポート番号の組(ソケット)で区別される。
  • データのやり取りを始める前に、送り手と受け手の間で TCP 接続(会話できる状態)を作る。
  • TCP 接続は、送り手の SYN・受け手の SYN/ACK・送り手の ACK という 3 回のやり取り(TCP ハンドシェイク、3 ウェイハンドシェイク)で作られる。
  • 2 回ではなく 3 回のやり取りが必要なのは、送り手と受け手それぞれが持つ情報が一致したことを、過不足なく確認できる回数が 3 回だからである。相手が応答しなければ、この会話できる状態は作れない。

しくみの話

IP は届く保証をしない(ベストエフォート)通信の上で、TCP は送った順番のとおり抜け落ちなく届くように管理し、届いたことの確認まで行う、信頼性のある通信の方法である(#44)。送り手と受け手は IP アドレスとポート番号の組(ソケット)で区別され、この組ごとに別々の TCP 接続を保てる(#71 p.5)。データのやり取りを始める前に、まず TCP 接続(会話できる状態)を作る(#4 p.5〜6)。この接続は、送り手の合図(SYN)、受け手の合図(SYN/ACK)、送り手の合図(ACK)という 3 回のやり取り、TCP ハンドシェイクで作られる(#71 p.7〜8)。2 回ではなく 3 回である理由は、送り手と受け手それぞれが持つ情報が一致したことを、過不足なく確認できる回数が 3 回だからである(#4 p.13〜14)。この 3 回のやり取りが終わって初めて、実際のデータのやり取りが始まる。

試してみよう

nc -zv example.com 443

見方: 「succeeded」を含む行が出れば、相手との間で 3 回のやり取りが完了し、会話できる状態が作れたことを意味する。失敗すると「refused」や「timed out」のような語が出る。

command not found などで動かなければ、読むだけで進んでよい。
