第 1 章 パケットの旅　1-1

「URL を開く」の裏で起きる 4 段階

このページでわかること

URL を入力してから画面が表示されるまでには、名前解決・接続・暗号化・要求と応答という 4 つの出来事がこの順で起きる。ここではHTTPS で新しく接続する場合を扱う(http の場合は暗号化の段階がない)。このページでは、この 4 つの出来事を順番に確認する。

このページの目次

かけあい

先輩に「URL が読めるんだから、そのまま繋げばいいのに、なんで IP アドレスも要るの?」って聞かれて、うまく答えられなかったんです。

良い質問ですね。ブラウザや途中の機械が実際に宛先として使うのは IP アドレスの方なんです。URL はあくまで人間向けの名前です。

じゃあ、URL を IP アドレスに変える作業が、どこかで挟まってるってことですか?

その通りです。今日はHTTPS で新しく接続する場合に絞って、URL を開くまでに起きる 4 つの出来事を順番に見ていきましょう。

4 つもあるんですか。全部教えてください。

名前解決、接続、暗号化、要求と応答の順に進みます。

名前解決って、URL のホスト名を IP アドレスに変える、さっきの話のことですよね?

そうです。ブラウザはDNSという仕組みに問い合わせて、ホスト名に対応する IP アドレスを教えてもらいます。詳しくは第 16 章で扱います。

IP アドレスが分かったら、もうデータのやり取りが始まるんですか?

まだです。次はその IP アドレス宛てにTCP 接続を作ります。手順の細かい中身は第 13 章に譲りますが、これで初めて相手と「会話できる状態」になります。

会話できる状態になったら、すぐ HTML をもらえるんですか?

https の場合はまだです。接続の直後に暗号化の手続きが入ります。ここでは、相手が本物のサーバかどうかを確かめるTLS 証明書を見せてもらいながら、この先のやり取りを守る鍵を決めます。

証明書って、鍵そのものじゃないんですか?

よくある誤解ですが違います。証明書は「相手が本物かどうかを確認する身分証」のようなもので、鍵はそれとは別に取り決めます。詳しくは第 18 章で扱います。

じゃあ http だと、その証明書の確認は無いってことですか?

はい。http には暗号化の段階そのものが無く、名前解決・接続・要求と応答の 3 段階で終わります。

暗号化まで終わったら、やっと本題ですね。

そうです。最後にブラウザが HTTP のルールに従ってページの中身を求め、サーバが応答を返します。

この 4 段階、順番を覚えておくと何がいいんですか?

どの段階で止まっているかが分かれば、疑うべき原因をかなり絞り込めます。名前解決なら DNS、接続や暗号化ならネットワークや証明書、要求と応答ならサーバ側、という具合です。

実際の障害対応でも、この 4 段階を 1 つずつ確認していくんですか?

そうです。名前解決の結果が正しいかをまず確認し、次に接続だけを確認する、というように 1 段階ずつ切り分けます。具体的なやり方は、道具を扱う章でまとめて練習します。

1 つずつ確認すれば、闇雲に疑うより早く原因にたどり着けそうですね。

その通りです。今日はまず、この 4 段階という地図を持ち帰ってください。

まとめ

  • URL を開く処理は「名前解決 → 接続 → 暗号化 → 要求と応答」の 4 段階に分けられる。
  • ここでは HTTPS で新しく接続する場合を扱う(http の場合は暗号化の段階がなく 3 段階で終わる)。
  • 名前解決で IP アドレスが決まって初めて、その IP アドレス宛ての TCP 接続を始められる。
  • 暗号化では TLS 証明書で相手を確認しながら、この先の通信を守る鍵を取り決める。
  • どの段階で止まっているかが分かれば、疑うべき原因(DNS、ネットワークや証明書、サーバ側のアプリケーションなど)をかなり絞り込める。

しくみの話

名前解決は、ホスト名を手がかりに DNS へ問い合わせ、対応する IP アドレスを受け取る処理である。接続は、その IP アドレス宛てに TCP 接続を確立する処理で、ここで初めてサーバとデータをやり取りできる状態になる。手順の細部(何回のやり取りで成立するかなど)は、接続を専門に扱う章で説明する。暗号化は TLS 証明書を使った手続きで、サーバがそれを提示し、ブラウザがそれを確認したうえで、この先の通信を守るための鍵を取り決める。要求と応答は、確立した通信路の上で HTTP のリクエストとレスポンスを 1 往復させる処理である。4 つの出来事は互いに独立しているため、名前解決の失敗はサーバへ 1 つもデータが届く前に起こり、接続の失敗は TCP 接続そのものが成立しない状態として現れ、暗号化の失敗は証明書の確認エラーとして現れる。http の場合はこの暗号化の段階自体が存在せず、名前解決 → 接続 → 要求と応答の 3 段階で完了する。この 4 つの出来事の切り分けは、後の章で障害を調査するときの基本的な考え方になる。例えば接続はできるのに応答が返らない場合、疑うべきはサーバ側のアプリケーションであって、名前解決やネットワークではない。

試してみよう

curl -sI https://example.com

見方: 1 行目に HTTP のバージョンと 200 のようなステータスコードが出れば、名前解決・接続・暗号化・要求と応答の 4 段階が全部成功して、応答が返ってきた証拠になる。

command not found などで動かなければ、読むだけで進んでよい。
