第 23 章 ロードバランシング　23-4

同じ人を同じサーバに送る

このページでわかること

同じ利用者からの複数回の要求を、できるだけ同じ機械に送り続ける仕組みがあることを確認する。この仕組みは、必ず同じ機械に届くことを保証するものではないという点も確認する。

このページの目次

かけあい

前のページで、同じ人の 2 回目の要求が別の機械に届くことがあるって聞きましたけど、それだと困る場合もありますよね?

あります。振り分け先の機械が、それまでのやり取りの内容を自分の中に覚えている場合です。

自分の中に覚えている、というのはどういうことですか?

例えば、大きなファイルを何回かに分けて送るとき、それまでに受け取った断片をどこまで持っているかを、機械が自分の中に一時的に覚えていることがあります。

同じ人からのリクエストを、同じ機械に送り続けることってできないんですか?

できます。同じ利用者からの複数回の要求を、できるだけ同じ機械に送り続ける仕組みがあり、セッションアフィニティ(スティッキーセッションとも呼ばれます)と呼びます。

個人開発で、大きなファイルを分割して送るアップロードを作ったとき、2 回目以降の断片を送ったら「続きが見つからない」と返されたことがあります。

それは、途中経過を自分の中だけに覚えていた機械と、次の断片を受け取った機械が別だったからだと考えられます。

セッションアフィニティを使っていれば、防げたんですね。

使っていなかったか、使っていても対応関係が崩れていたかのどちらかです。

じゃあ、これを使えば絶対に同じ機械に届くんですね?

そうとも限りません。振り分け先の機械の数が変わったり、健康状態が変わったりすると、この対応関係が崩れることがあります。

絶対に保証されるわけじゃないんですね。

そうです。ベストエフォート、つまり最善は尽くすけれど保証はしない、という位置づけです。

どういうときに、対応関係が崩れやすいんですか?

例えば、ヘルスチェックで機械が外れたり戻ったりするときや、振り分け先の台数そのものが変わるときです。

前のページで見たヘルスチェックとも、関係あるんですね。

そうです。この章で見てきた仕組みは、それぞれ単独ではなく、組み合わさって動いています。

さっき「既定では組み合わせで振り分け先が決まる」って言ってましたけど、これって前のページのフローハッシュのことですか?

近い考え方です。既定では、送信元・宛先の IP アドレスやポート番号、通信の種類などの組み合わせをもとに振り分け先が決まります。この組み合わせが変われば、別の機械が選ばれることがあります。

セッションアフィニティを使うと、その組み合わせの見方が変わるんですか?

変わります。送信元の IP アドレスだけ、あるいは送信元の IP アドレスと通信の種類の組み合わせだけを見るようにして、より多くの要求が同じ機械に固定されるようにします。

まとめ

  • 振り分け先の機械が、それまでのやり取りの内容を自分の中に覚えている場合、同じ利用者の要求は同じ機械に送り続ける必要がある。
  • 同じ利用者からの複数回の要求を、できるだけ同じ機械に送り続ける仕組みを、セッションアフィニティ(スティッキーセッション)と呼ぶ。
  • 大きなファイルを分割して送るアップロードで、2 回目以降の断片が別の機械に届くと、途中経過を知らないその機械が「続きが見つからない」と返すことがある。
  • セッションアフィニティはベストエフォートであり、振り分け先の機械の数や健康状態が変わると、対応関係が崩れることがある。
  • 前のページで見たラウンドロビンやフローハッシュだけでは、同じ利用者の要求が別の機械に届くことがあり、セッションアフィニティはこれを補う仕組みである。
  • 既定の組み合わせ(フローハッシュに近い考え方)ではなく、送信元の IP アドレスなど少ない要素だけを見るようにすることで、セッションアフィニティは同じ機械への固定を実現する。

しくみの話

同じ利用者からの複数回の要求を、できるだけ同じ振り分け先に送り続ける仕組みを、セッションアフィニティ(別名スティッキーセッション)と呼ぶ(#93)。振り分け先の機械が、それまでのやり取りの内容(進行中の作業の状態など)を自分の中に一時的に覚えている場合に使われる(#93)。既定では、送信元・宛先の IP アドレスやポート番号、通信の種類などの組み合わせ(23-2 で見たフローハッシュに近い考え方)で振り分け先が決まるため、これだけでは同じ利用者の要求でも別の機械に届くことがある(#93、#94)。セッションアフィニティを使うと、送信元の IP アドレスなど、より少ない要素の組み合わせで振り分け先を固定できる(#94)。ただし、この対応関係はベストエフォートであり、振り分け先の機械の数や健康状態が変わると崩れることがある(#93)。

参考文献

  • [#93] Google Cloud「Backend services overview」(Session affinity の節) — 原典(1219〜1230 行目「Session affinity」の節。同じ利用者からの複数の接続を同じ振り分け先に送る仕組みで、ステートフルなサーバや内部キャッシュを多用するサービスで有用という記述。1228 行目「Google Cloud load balancers provide session affinity on a best-effort basis.」というベストエフォートの明示。1237 行目。既定は送信元・宛先の IP アドレスとポート番号、プロトコルの組み合わせ〈五要素〉によるハッシュという記述)
  • [#94] Microsoft「Azure Load Balancer distribution modes」 — 原典(20〜32 行目「Hash based」の節。既定は五要素のハッシュで、同じ送信元から新しいセッションが始まると送信元ポートが変わり、別の機械に届きうるという記述。41〜48 行目「Session persistence」の節。別名がセッションアフィニティ・送信元 IP アフィニティであるという記述、送信元と宛先の IP アドレスの組み合わせ〈2 要素〉、またはこれにプロトコルを加えた組み合わせ〈3 要素〉で振り分け先を固定するという記述)
