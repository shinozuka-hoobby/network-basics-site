第 31 章 総合演習 — 「つながらない」「遅い」を層で切り分ける　31-2

名前が解けているかを、まず確かめる

このページでわかること

「名前が解けない」「古い IP アドレスに行く」という症状を、dig の結果だけで見分ける。この段階で原因が確定すれば、それより後の段階は確かめる必要が無い。

このページの目次

かけあい

ケース 1、練習してみましょう。「名前が解けない」とか「古い IP アドレスに行く」っていう症状でしたよね。

そうです。31-1 の①、まず dig で確かめます。

第 17 章 17-1 で、レコードを書き間違えて「このサイトにアクセスできません」が出た話がありましたよね。

よく覚えていますね。あの状況を、31-1 の手順に当てはめて見直してみましょう。

dig を実行すると、どこを見ればいいんですか。

status の行を見てください。NXDOMAIN と出れば、名前が存在しないという確定した答えです。

確定した答え、っていうのはどういう意味ですか。

dig 自体は正しく問い合わせを処理していて、その結果として「無い」と分かった、という意味です。dig 自体が失敗したわけではありません。

じゃあ NXDOMAIN が出たら、それより後の段階、例えば経路とか証明書とかは、もう疑わなくていいんですか。

疑う必要はありません。名前が存在しないという答えが確定している以上、後の段階を確かめても手がかりにならないからです。

なるほど、31-1 で見た考え方そのものですね。じゃあ「古い IP アドレスに行く」方は、どう見分けるんですか。

第 1 章 1-2 で見た、サーバを引っ越したのに古いサーバへ繋がり続けた話を覚えていますか。

はい、TTL とキャッシュの話でしたよね。

そうです。あちらは NXDOMAIN にはならず、答え自体は返ってきます。dig の ANSWER の区画に出る IP アドレスと TTL の数字を見てください。

TTL の数字を見て、どう判断すればいいんですか。

複数の場所に残ったキャッシュの控えが、まだ古い答えを保持している可能性を疑います。時間を置いて聞き直すと、新しい答えに変わっていることがあります。

SERVFAIL の場合はどうですか。

SERVFAIL は、権威サーバに届かなかったり、時間内に答えが得られなかったりして、答えそのものを返せなかった失敗です。レコードの書き間違いとは、原因の性質が違います。

NXDOMAIN は「無いという確定した答え」、SERVFAIL は「答えを返せなかった失敗」ってことですね。

そのとおりです。

第 27 章 27-3 で、dig コマンド自体の終了コードと、DNS の答えの中身は別物だっていう話がありましたよね。

そうです。NXDOMAIN や SERVFAIL が返ってきても、dig 自体は正常に動作しています。この区別を混同すると、原因を見誤ります。

dig の結果 1 つで、原因の見当がだいぶ絞れるんですね。ケース 1 は、これで終わりですか。

そうです。31-1 の①の段階だけで完結する、3 つのケースの中でも比較的見分けやすいケースでした。次のケースでは、握手の段階、TLS と証明書を見ていきましょう。

まとめ

  • dig の status が NXDOMAIN なら、名前が存在しないという確定した答えであり、それより後の段階を疑う必要は無い。
  • SERVFAIL は、権威サーバに届かなかったり時間内に答えが得られなかったりして、答えそのものを返せなかった失敗であり、NXDOMAIN とは原因の性質が違う。
  • 「古い IP アドレスに行く」症状は、dig の ANSWER の区画に出る IP アドレスと TTL の数字を見て、キャッシュに残った古い答えをまだ使っている可能性を疑う。
  • ケース 1 は、31-1 の①(名前解決)の段階だけで完結する、3 つのケースの中でも切り分けやすいケースである。

しくみの話

第 17 章 17-1 で確立したとおり、NXDOMAIN は指定した名前がそもそも存在しないと分かったときに返ってくる、確定した答えである(#83)。SERVFAIL は、権威サーバに届かなかったり時間内に答えが得られなかったりして、答えそのものを返せなかった失敗である(#32)。DNS レコードの登録時に名前を書き間違えると、意図した名前に対応する情報が権威サーバに無い状態になり、NXDOMAIN が返ってくることがある(#53)。dig 自体の成否とこれらの答えは別物であり、NXDOMAIN や SERVFAIL が返ってきたということは、dig 自体は問い合わせを正しく処理できている。第 1 章 1-2 で確立したとおり、名前解決の答えには TTL という期限があり、複数の場所に残ったキャッシュの控えが期限内であれば、レコードを直した後もしばらく古い答えが返り続けることがある(#52、#12)。

試してみよう

dig example.com
dig nosuchname.example.com

見方: 2 つの結果の status の行を比べる。存在する名前(example.com)では NOERROR、存在しない名前(nosuchname.example.com)では NXDOMAIN になる。31-1 の手順に当てはめると、NXDOMAIN であれば①の段階で原因が確定し、それより後の段階を確かめる必要が無いと判断できる。

2 行目は存在しないことが分かっている名前への問い合わせのため、通常の試してみようで使う候補(example.com など)とは違う名前を使っている。command not found などで動かなければ、読むだけで進んでよい。
