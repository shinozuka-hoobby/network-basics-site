第 22 章 CDN とキャッシュ　22-2

何を、いつまで控えるか

このページでわかること

エッジサーバが控えを返してよいかどうかは、要求の内容を比べて判断される。その判断材料と、控えを使ってよい期限は、それぞれ別の役割を持つ。このページでは、その 2 つを確認する。

このページの目次

かけあい

エッジサーバに控えがあるかどうかって、どうやって決まるんですか? 同じ URL ならいつも同じ答えが返ってくるんですか?

基本はそうです。同じ URL への、同じ種類の要求(GET など)かどうかを比べて、同じ控えを返してよいかを判断します。この判断材料の組み合わせを、キャッシュキーと呼びます。

第 20 章 20-5 で見た HTTP キャッシュと同じ話ですか?

そうです。CDN の控えは、あの HTTP キャッシュの延長で、控える場所が利用者の近くの専用の機械になったものと考えてください。

じゃあ、控えはいつまでも使い続けていいんですか?

いいえ。控えにも、この秒数の間は使ってよいという期限があります。これをキャッシュの TTLと呼びます。

第 16 章で見た DNS の TTL と、同じ名前ですね。

名前は同じですが、DNS の TTL は名前解決の答えを覚えておいてよい秒数、キャッシュの TTL はコンテンツの控えを使ってよい秒数で、対象が違います。

この期限って、誰が決めるんですか?

Web サーバの応答に添える指示で決まります。第 20 章 20-5 で見た Cache-Control が、その指示です。

Cache-Control って、20-5 でも出てきましたね。

そうです。あのページで見た「この秒数までは使ってよい」という指定が、CDN の控えにもそのまま関係してきます。

この TTL って、サイト全体で 1 つに決まってるものなんですか?

いいえ。TTL は控え 1 つ 1 つに付く期限なので、ページごとや画像ごとに違っていて構いません。

このキャッシュキーの考え方って、誰かが厳密に決めているんですか?

細かい決め方はこの講座の範囲を超えますが、基本の考え方として、同じ要求先・同じ種類の要求かどうかで判断される、と覚えておいてください。

同じ URL への要求でも、聞くたびに答えが変わることってあるんですか?

キャッシュキーが同じであれば、期限が来るまでは同じ控えが返り続けます。答えが変わるとしたら、期限が来て取り直したときです。

キャッシュキーと TTL、どちらも控えに関わるけど役割が違うんですね。

そのとおりです。キャッシュキーは何が同じ答えの対象かを見分けるもの、TTL はいつまで使ってよいかを見分けるもの、という違いです。

まとめ

  • 何が同じなら同じ控えを返してよいかを判断する材料の組み合わせを、キャッシュキーと呼ぶ。基本は、要求先の URL と、GET などの要求の種類で決まる。
  • 控えを、この秒数の間は使ってよいとする期限を、キャッシュの TTL と呼ぶ。
  • キャッシュの TTL は、Web サーバの応答に添える指示(第 20 章の Cache-Control)で決まり、控え 1 つ 1 つに付く期限なので、ページごとや画像ごとに違っていてよい。
  • 第 16 章で見た DNS の TTL とは、名前は同じでも、覚えておく対象(名前解決の答えか、コンテンツの控えか)が違う。
  • CDN の控えの仕組みは、第 20 章で見た HTTP キャッシュの延長で、控える場所が利用者の近くの専用の機械になったものである。
  • キャッシュキーが同じであれば、期限が来るまでは同じ控えが返り続け、答えが変わるのは期限が来て取り直したときである。

しくみの話

エッジサーバが、同じ要求に対して同じ控えを返してよいかどうかを見分けるために比べる材料の組み合わせを、キャッシュキーと呼ぶ。基本は、要求先の URL と、GET などの要求の種類で決まる。例えば、同じサイトの中でも、あるページの URL と別のページの URL は、それぞれ別のキャッシュキーとして扱われ、別々に控えが管理される。控えには、この秒数の間は使ってよいとする期限があり、これをキャッシュの TTL と呼ぶ(#63)。この期限は、第 20 章 20-5 で見たとおり、Web サーバが応答に添える Cache-Control という指示で決まる。TTL は控え 1 つ 1 つに付く期限であり、ページごとや画像ごとに違っていてよい(#63)。第 16 章 16-4 で見た DNS の TTL とは、名前は同じだが、DNS の TTL は名前解決の答えを覚えておいてよい秒数、キャッシュの TTL はコンテンツの控えを使ってよい秒数で、対象が異なる。CDN の控えの仕組みは、第 20 章で見た HTTP キャッシュの延長にあり、控える場所が利用者の近くの専用の機械になったものと言える。この 2 つの考え方(キャッシュキー、キャッシュの TTL)を理解しておくと、思いどおりに控えが更新されないときに、どちらが原因かを切り分けやすくなる。

試してみよう

curl -sI https://example.com

見方: 応答の中の "age" という行の数字を見てください。この数字は、その控えが作られてからの経過秒数です。この秒数が、控えを使ってよい期限(キャッシュの TTL)に達すると、次の要求のときにはオリジンサーバへ取り直しに行きます。

command not found などで動かなければ、読むだけで進んでよい。
