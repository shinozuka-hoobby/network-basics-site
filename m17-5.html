第 17 章 DNS の運用と障害　17-5

クラウドの DNS は、何を単位に設定するか

このページでわかること

クラウドの DNS サービスを使うとき、何を単位に設定すればよいのか。第 16 章で見たゾーンという考え方が、そのまま設定の単位になっている。このページでは、3 社の呼び名の違いと、レコードの置き方を確認する。

このページの目次

かけあい

クラウドで DNS を使うとき、何を単位に設定すればいいんですか? 第 16 章で見たゾーンと関係あるんですか?

まさにそのゾーンが、そのまま設定の単位になります。ただ、事業者ごとに呼び名が違います。

例えばどう違うんですか?

AWS の Route 53 では hosted zone、Google Cloud の Cloud DNS では managed zone、Azure の Azure DNS では DNS zone と呼びます。

呼び名はバラバラですけど、指しているものは同じなんですか?

同じ考え方です。あるドメインとそのサブドメインの DNS レコードをまとめて入れる入れ物、という点はどの事業者でも共通しています。

レコードは、このゾーンの中に置くってことですね。

そうです。DNS レコードを追加・変更するときは、このゾーンを指定して操作します。

ゾーンには、どんな種類のレコードでも置けるんですか?

置けます。第 16 章で見た A・AAAA・CNAME・NS・MX・TXT といった DNS レコードは、どれもこのゾーンの中に置かれます。

3 社を乗り換えるときも、この「ゾーン」という考え方は変わらないんですか?

変わりません。呼び名は違っても、レコードをまとめて管理する入れ物という役割はどの事業者でも同じなので、考え方はそのまま持っていけます。

ゾーンさえ作れば、すぐに使えるようになるんですか?

もう一つ手順があります。ドメインを最初に登録したレジストラ(ドメインの登録先の会社)には、そのドメインを管理する権威サーバの名前を伝えておく必要があります。

なんでレジストラにも伝える必要があるんですか?

ドメインの登録情報には、そのドメインの権威サーバの名前も含まれています。ここが正しく設定されていないと、DNS リゾルバがそもそもどこに聞きに行けばいいか分かりません。

そこも第 16 章で見た、権威サーバの話とつながってるんですね。

そのとおりです。

3 社の呼び名、ちゃんと覚えておいたほうがいいんですかね。

覚えるというより、「呼び名が違っても、指しているものは同じ」という考え方を押さえておけば十分です。

これで、DNS の運用と障害について、一通り見てきましたね。

そのとおりです。名前が無い場合、答えられない場合、伝わるまでの時間差、遅くなる原因、本物かどうかの確認、そしてクラウドでの設定の単位まで、一通り確認できました。

まとめ

  • クラウドの DNS サービスでは、第 16 章で見たゾーンがそのまま設定の単位になっている。
  • AWS の Route 53 では hosted zone、Google Cloud の Cloud DNS では managed zone、Azure の Azure DNS では DNS zone と呼ぶが、指している考え方は同じである。
  • DNS レコードは、このゾーンの中に置き、追加・変更もゾーンを指定して行う。
  • ドメインを最初に登録したレジストラには、そのゾーンを管理する権威サーバの名前を伝えておく必要がある。
  • 呼び名は事業者ごとに違っても、「あるドメインとそのサブドメインのレコードをまとめて入れる入れ物」という考え方は共通している。

しくみの話

クラウドの DNS サービスでは、第 16 章で見たゾーンという考え方が、そのまま設定の単位になっている。AWS の Route 53 では hosted zone、Google Cloud の Cloud DNS では managed zone、Azure の Azure DNS では DNS zone と呼ぶ(#24、#32、#41)。呼び名は違っても、あるドメインとそのサブドメインの DNS レコードをまとめて入れる入れ物という考え方は共通しており、DNS レコードの追加・変更は、このゾーンを指定して行う。また、ドメインを最初に登録したレジストラ(ドメインの登録先の会社)には、そのドメインを管理する権威サーバの名前を伝えておく必要がある。ドメインの登録情報に権威サーバの名前が含まれていないと、DNS リゾルバはどこに問い合わせればよいか分からない(#24)。
