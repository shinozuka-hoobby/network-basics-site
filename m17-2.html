第 17 章 DNS の運用と障害　17-2

変更が「伝わる」の正体

このページでわかること

DNS レコードを変更しても、すぐには新しい答えに切り替わらないことがある。よく「変更が伝播するまで待つ」と言われるが、実際に起きているのは、権威サーバへの反映と、各地に残った DNS キャッシュの期限切れという、性質の違う 2 つの段階である。このページでは、この 2 段階の正体を確認する。

このページの目次

かけあい

DNS レコードを変更したとき、「変更が伝播するまで待つ」って言い方を先輩がしてました。第 16 章で見た DNS の TTL と DNS キャッシュの話と同じことですか?

近い話ですが、もう一歩踏み込むと、その「伝播」という言い方は少し正確ではありません。

え、どういうことですか?

変更は 2 段階で反映されます。まず、変更した内容が権威サーバに書き込まれる段階。次に、各地の DNS リゾルバが持っている古い答えの DNS キャッシュが、期限切れになって初めて新しい答えを取り直す段階です。

じゃあ、新しい答えが古いキャッシュに「押し出されて」広まっていくわけじゃないんですね?

そうです。押し出されるのではなく、それぞれの DNS リゾルバが自分の DNS の TTL が切れたタイミングで、勝手に取り直しに行くだけです。

権威サーバへの反映のほうは、すぐに終わるんですか?

管理画面や API で変更を保存すれば、権威サーバ側はすぐに新しい内容になります。時間がかかるのは、その先の DNS キャッシュの取り直しのほうです。

先輩から、DNS の TTL を 1 日にしたまま移行したら、切り替えが丸 1 日終わらなかったという話を聞いたことがあります。

DNS の TTL が高すぎると、DNS リゾルバが古い答えを長く覚えたままになるので、切り替えに時間がかかります。だいたい 86400 秒(24 時間)が典型的な上限で、多くのサービスはもっと短く、6 時間以下に設定しています。

じゃあ、切り替えの予定が決まっているときは、前もって DNS の TTL を短くしておくといいんですね。

そのとおりです。短くしすぎると問い合わせの回数が増えるという別の負担もあるので、普段は程よい長さにしておき、予定が分かっているときだけ短くしておくのがよくあるやり方です。

なるほど、「伝播」っていう言葉のイメージだけで考えると、勘違いしそうですね。

そうです。実際に起きているのは、権威サーバへの反映と、DNS キャッシュの期限切れという、別々の 2 つの出来事です。

権威サーバへの反映自体が失敗することもあるんですか?

あります。設定の保存操作そのものが失敗すれば、その時点で反映されません。ただし、それは今回見てきた「時間差」とは別の問題です。

この 2 段階、自分で確認する方法ってあるんですか?

権威サーバへの反映そのものを外から直接見る方法はありません。DNS キャッシュの期限切れのほうは、前の章で DNS の TTL の数字を見て確認しましたね。

まとめ

  • 俗に「伝播」と呼ばれる現象の正体は、権威サーバへの反映と、各地の DNS キャッシュの期限切れという、性質の異なる 2 段階である。
  • 新しい答えが古いキャッシュに押し出されるのではなく、各 DNS リゾルバが自分の DNS の TTL が切れたタイミングで勝手に取り直すだけである。
  • 管理画面や API での変更の保存自体は、権威サーバ側にはすぐに反映される。時間がかかるのは、その先の DNS キャッシュの取り直しである。
  • DNS の TTL が高すぎると、切り替えに時間がかかる。典型的な上限は 86400 秒(24 時間)で、多くのサービスはそれより短く 6 時間以下に設定している。
  • 切り替えの予定が決まっているときは、前もって DNS の TTL を短くしておくと、この時間差を短くできる。

しくみの話

DNS レコードの変更は、俗に「伝播」と呼ばれるが、実際には 2 つの別々の段階で起きる。まず、変更した内容が権威サーバに書き込まれる段階。次に、各地の DNS リゾルバが持つ DNS キャッシュが、それぞれの DNS の TTL の期限切れ後に新しい答えを取り直す段階である(#32「Propagation of changes」)。新しい答えが各地のキャッシュへ能動的に配られるわけではなく、DNS リゾルバ側がそれぞれ独自のタイミングで期限切れを迎え、取り直しに行くだけである。DNS の TTL が高いと、DNS リゾルバは古い答えを長く覚えたままになり、変更がゆっくりとしか反映されない。典型的な上限は 86400 秒(24 時間)だが、多くのサービスはそれより短く、6 時間以下に設定している(#53「Time-to-live (TTL) is set too high」)。切り替えの予定が決まっている場合は、前もって DNS の TTL を短くしておくことで、この時間差を短くできる。
